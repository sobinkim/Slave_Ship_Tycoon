# 게임 플레이 스타일과 새 세션 기준

이 문서는 새 세션에서 기획·밸런스·전투 QA를 시작할 때 먼저 읽는 현재 게임의 요약입니다. 아래의 코드·에셋 상태는 확인된 사실이고, 제안이나 미구현 기능은 따로 표시합니다. 문서와 현재 코드·Inspector가 다르면 실제 연결과 동작을 다시 확인하고 이 문서를 갱신합니다.

## 한 문장 요약

이 게임은 **함대를 편성하고 함선 위치·역할을 준비한 뒤, 자동 전투 결과와 성장·화물 운송으로 다음 도전을 준비하는 2D 해상 방치형 게임**입니다. 실시간 조준과 직접 조종보다 함선 종류, 배치, 타겟 규칙, 함대 성장에 판단이 실립니다.

## 플레이어가 하는 판단

- 함대 화면에서 보유 호위선을 골라 슬롯에 배치합니다. 함선 카드를 고른 뒤 편성 슬롯을 선택하는 흐름이며, 전투가 시작된 뒤 슬롯을 실시간으로 옮기는 방식은 아닙니다.
- 함선별 체력·공격력·공격 속도와 함대 강화, 지휘 스킬을 준비합니다. 전투 중 함선은 자동으로 표적을 고르고 공격합니다.
- 챕터의 경로와 보스 진입에 맞춰 화물을 적재하고, 운송 구간과 정산을 진행합니다.

개별 함선의 표적은 `TargetSelector`의 전열/중열/후열 및 `ShipRole` 규칙, 선택 모드, 배치 슬롯을 바탕으로 정해집니다. 일반 공격은 플레이어가 매 발사마다 직접 조준하는 구조가 아닙니다. 지휘 집중 공격은 살아 있는 적의 가장 앞 열을 지정하는 기존 기능입니다. 함선 `Role` 값은 분류·타겟 우선순위에 쓰이며, 그 값을 넣는 것만으로 고유 능력이 생기지는 않습니다. 보호·회복·요격·연막 같은 실제 효과는 해당 컴포넌트와 데이터 연결을 확인합니다.

현재 `ShipRole` 표시는 Tanker, Dealer, Support, Speedster, AoE, Piercer입니다. 이들은 타겟 규칙에서 쓸 수 있는 역할 태그이며, 함선의 고유 행동과 같은 뜻은 아닙니다. `TargetSelectionMode`에는 배치 분산, 현재 체력 높음/낮음, 규칙 후보 무작위, 가장 가까운 대상 선택이 있습니다.

## 배치가 전투를 바꾸는 방식

현재 아군 배치는 **3열×3행 격자**입니다. 본함은 후열 중앙 `(x=0, y=1)`에 고정되고, 호위선은 나머지 8칸을 사용합니다. 화면에서 위·아래 어느 행이 되는지는 Spawn Point의 Y 좌표가 정합니다.

| 아군 행 | 후열 `x=0` | 중열 `x=1` | 전열 `x=2` |
|---|---|---|---|
| 위 | 호위 슬롯 7 | 슬롯 1 | 슬롯 2 |
| 가운데 | 본함 | 슬롯 3 | 슬롯 4 |
| 아래 | 호위 슬롯 8 | 슬롯 5 | 슬롯 6 |

적의 기본 배치는 **3열×4행, 최대 12칸**입니다. 슬롯은 행 우선으로 저장되며 적의 전열은 `x=0`, 중열은 `x=1`, 후열은 `x=2`입니다. 아군 전열은 `x=2`, 후열은 `x=0`입니다. 양쪽 모두 전열은 상대를 향하지만 X 인덱스는 서로 거울처럼 반대입니다. Transform의 실제 좌표를 옮겨도 논리 열은 슬롯 인덱스에서 정합니다.

배치가 만드는 구체적 차이:

- 공격자는 자신의 슬롯에 따라 `FormationDistribution` 타겟 선택이 달라질 수 있습니다. 각 함선의 타겟 규칙은 적의 논리 열과 역할을 우선순위대로 검사합니다.
- `ImmediateRearProtection` 방어함은 같은 행의 인접 칸만 보호합니다. 아군 전열 공급함 `x=2`는 바로 뒤 중열 `x=1`을 보호하고, 적 전열 공급함 `x=0`은 `x=1`을 보호합니다. 빈 칸을 건너뛰어 더 뒤의 함선을 보호하지 않습니다.
- 직접 보호 대상은 일반 공격 타겟에서 제외될 수 있으며, 보호 효과의 피해 감소는 별도 적용됩니다. 습격함처럼 보호된 적을 겨냥할 수 있는 함선은 `Can Target Protected Ships`와 공격 설정을 확인합니다.
- 연막·회복·요격 등 함선 종류의 차이는 실제 타겟 규칙과 효과 컴포넌트에 따라 나타납니다. 함선 이름이나 역할만 보고 능력을 추정하지 않습니다.

세부 슬롯 대응과 구현 절차는 [스폰 위치와 함선 정렬](../UserGuide/05_스폰위치와_함선정렬.md), [스탯과 공격 대상 설정](../UserGuide/07_스탯과_공격대상_설정.md), [보호 효과](../UserGuide/09_보호효과와_방패_아이콘.md), [함선 제작](Ship_Creation.md)을 참고합니다.

## 기본 진행 흐름

`GameFlowManager`가 챕터 경로를 관리합니다.

1. `Obtain` 경로의 일반 웨이브를 반복해 자원과 보상을 얻습니다. 일반 전투를 클리어하면 다음 웨이브가 이어집니다.
2. 화물 적재 화면에서 용량과 예상 기본 수익을 확인하고 보스를 도전할 수 있습니다. 보스 도전은 유효한 화물 적재와 해당 챕터의 보스 레이아웃이 필요합니다.
3. 보스를 처치하고 다음 챕터가 `Sell` 경로라면 화물 매니페스트를 준비합니다. 정해진 운송 구간을 진행한 뒤 시세와 정산을 거칩니다.
4. 적 함대를 모두 처치하면 현재 전투는 클리어되고, 본함이 파괴되면 실패합니다. 결과와 다음 진행은 챕터 경로에 따라 달라집니다.

해적 세력 `Obtain` 챕터의 일반 전투는 현재 `SeaCreatureSurvivalDirector`가 크리쳐 조우를 진행할 수 있습니다. 보스 전투는 기존 적 함대 레이아웃 경로를 사용합니다. 따라서 “해적 챕터의 모든 일반 전투가 해적 함대전”이라고 가정하지 않습니다. 상세 흐름은 [전체 구조와 실행 흐름](../UserGuide/01_전체구조와_실행흐름.md)과 [UI Toolkit 인게임·화물](UI_InGame_Cargo.md)을 확인합니다.

## 현상금 추적을 논의할 때

2026-10-22 **현상금 추적 프로토타입을 SampleScene에 구현했습니다.** 기존 현상금 이미지 버튼에서 시작하며, 고정 60초 안에 메인 해적선을 격침하면 성공합니다. 목적지 도착 또는 기존 본함 침몰 처리 시 실패합니다. 4척 기본 편성과 연막함을 추가한 5척 편성, 밤바다·하늘, 전용 외형·HUD·결과·재도전·파밍 복귀가 연결되어 있습니다. 실제 연결·조절값·검증 범위는 [현상금 추적](Bounty_Pursuit.md)을 참고합니다.

현상금 추적은 기존 자동 전투·호위 배치·보호·요격·연막·함선별 타겟 규칙을 사용합니다. `BattleManager`의 일반 승리 조건인 적 전멸에 더해, 추적전에서 지정한 메인 해적선 사망으로 성공을 판정합니다. `BountyPursuitController`가 도주 시간과 결과를 관리하고, `GameFlowManager`는 추적 중 일반 챕터 진행을 보류합니다.

용어도 기존 전투 열과 추격 방향을 구분합니다. 기존 적의 `전열`은 플레이어를 향하는 `x=0`입니다. 해적의 도주 방향을 설명할 때는 **도주 선두·목적지 쪽 호위·추격자 쪽 후미 방어선**처럼 목적지 기준 표현을 사용하고, 이를 현재 `Front/Back`과 자동으로 같은 뜻이라고 보지 않습니다.

사용자는 프로토타입에서 이동·도주 시간을 고정하기로 결정했습니다. 별도 이동 속도 성장 대신 기존 함선 종류·배치·공격 규칙과 성장 수치로 제한 시간에 대응합니다. 목표 함선의 명칭은 **메인 해적선**입니다.

## 2026-10-22 QA 관찰과 범위

- Unity `6000.0.59f2`, `Assets/SB/Animations/Scenes/SampleScene.unity`의 실제 Game 뷰를 확인했습니다. 기존 실행 중 화면에서는 아군이 왼쪽, 적이 오른쪽에 여러 행으로 배치되고 발사체·방어 효과가 보이는 자동 교전을 관찰했습니다.
- Editor를 재생 모드로 다시 시작한 뒤에는 **화물 적재 화면**이 열렸습니다. 적재 중량, 예상 기본 수익, 화물별 수량 조절, 남은 용량, 보스 도전 버튼이 한 화면에 나타났습니다.
- 프로젝트의 Windows 입력 브리지는 이번 세션에서 앱 창을 반환하지 않았습니다. 따라서 메뉴 버튼을 실제로 눌러 편성 변경, 보스 도전, 전투 승패까지 이어지는 수동 QA는 수행하지 않았습니다. 화면과 코드 경로를 확인한 범위의 QA입니다.
- 재생 시작 시 콘솔에 기존 오류 `MerchantLedger needs an icon.`이 기록됐습니다. `TransportEquipmentManager.TryEquip`에서 발생하며 이번 문서 변경으로 생긴 오류는 아닙니다. 캡처 툴이 Edit Mode의 `source="screen"` 요청을 거부한 로그도 있었지만, 이 역시 게임 플레이 오류가 아닙니다.
